# AI 监听任务设计

状态：设计提案，尚未接入业务执行。日期：2026-10-03。

交互方案源文件：`docs/prototypes/ai-listening-tasks.html`（自包含 HTML 片段，使用示例数据）。已验证新增任务、多选账号/Skills、保存、编辑保留暂停状态、暂停恢复、首次恢复历史入队、补生成预估及详情日志；脚本语法检查通过。业务代码尚未按此提案实现。

## 1. 产品目标

用户在 `/ai-writing` 保存一条长期运行的监听任务：选择账号、监听模式和一组 Skills。符合条件的内容被采集后，系统调用已配置的 AI 数据源生成文章草稿；用户能看到任务是否生效、排队情况、成功/失败数量、每次尝试及错误原因。

推荐第一版采用“一条符合条件的源推文 → 一篇文章草稿”。多个账号是内容来源范围，不自动将它们合并成一篇文章。默认只生成草稿，进入文章管理后由用户编辑、发布。

“监听任务”是可保存、启停的长期配置；“生成记录”是某条源内容在某个任务下的一次生成结果。一个监听任务可以持续产生很多生成记录。

## 2. 页面结构

Tab 顺序建议调整为：**监听任务 / 生成记录 / Skills / 创作设置 / AI 数据源**。

- 当前用户上下文（代码中已有 `context`/“监听配置”）由监听任务取代，原作者画像移入账号详情或任务详情的账号区域。
- 当前生成任务改名生成记录，继续显示所有手动、监听、旧自动生成的结果，可按来源和监听任务筛选。
- Skills 保持统一管理；监听任务和 `/tweets` 手动生成都选用同一份已启用 Skills。
- 创作设置保留 AI 总开关、默认语言/语气、重试与超时等；自动触发由监听任务配置决定。
- AI 数据源第一版复用现有唯一数据源。任务显示其名称、模型与连接状态，不重复填写 API Key。

### 2.1 监听任务列表

页头：新增任务、刷新、AI 数据源/Worker 就绪状态。

| 列 | 展示内容 |
| --- | --- |
| 任务名称 | 可点开详情；最近命中/生成活动时间 |
| 监听范围 | 具体账号或全部监听账号；超长内容折叠并可展开 |
| 监听模式 | 全部 / 原创 / 回复 / 转推（含引用） |
| Skills | 选中的 Skill 名称，完整列表可查看 |
| 状态 | 已启用 / 已暂停 / 配置异常 / 已归档，并显示原因 |
| 执行情况 | 排队、执行中、等待重试的当前数量 |
| 结果 | 成功数、最终失败数 |
| 累计执行尝试 | 每次 Worker 执行都计数，手动重试不清零 |
| 操作 | 详情、编辑、暂停/恢复、复制、归档 |

统计来自后端全部记录，不以当前分页行数计算。状态、失败数、排队数均可进入对应详情，不能用“最近一篇失败”推断整个监听任务异常。

### 2.2 新增/编辑任务

采用右侧抽屉承载配置，交互与 QQ 群目标新增一致，适应更多字段；窄屏变为整页表单。

| 配置 | 推荐默认值和规则 |
| --- | --- |
| 任务名称 | 必填，例如“AI 产品动态分析” |
| 监听账号 | 指定账号多选，至少 1 个；可切换全部账号 |
| 全部账号语义 | 自动覆盖后来新增的监听账号；不会自动创建账号或扩大账号采集范围 |
| 监听模式 | 默认原创；与 QQ 一致，支持全部、原创、回复、转推（含引用） |
| 生成 Skills | 必选 1–20 个已启用 Skill；可查看说明和指令；按所选顺序展示和应用 |
| AI 数据源 | 展示当前全局数据源和模型，可跳转设置 |
| 首次历史范围 | 默认“从启用时刻开始”；可选最近 1/3/7 天或自定义天数，仅新建时配置 |
| 生成方式 | 第一版固定每条源内容生成一篇文章草稿 |
| 高级配置 | 默认继承创作设置；必要时覆盖最大尝试次数、语言、语气和输出上限 |
| 保存行为 | 新建时“保存并启用”为主按钮，另有“保存为暂停”；编辑时“保存修改”，保留原启停状态，恢复使用独立操作 |

保存前提供可读摘要：“监听 3 个账号的原创内容，使用 2 个 Skills，生成文章草稿；首次处理最近 3 天的已采集内容。”

选择回溯时先查询预计匹配数及去重后的待生成数，显示历史范围和预估工作量。查询只读，不调用 AI；用户点保存并启用后才创建回溯队列。回溯异步分批执行，界面显示扫描进度和已入队数量。

保存为暂停的任务尚未设置 `activated_at`；首次启用才锚定启用时间、重新预估并启动已选历史回溯。此后的暂停/恢复不重新启动首次回溯。任务详情的“补生成历史”支持另外提交固定范围；暂停时可保存待执行的回溯请求，扫描和生成均等待恢复。

账号未启用采集、账号关闭包含回复/转推、无有效 Skills、数据源未配置或 Worker 离线时，显示具体影响。账号采集选项不会被任务表单静默修改。

### 2.3 任务详情

- 配置摘要：名称、账号、模式、Skills、配置版本、启用时间、数据源。
- 执行概况：成功、最终失败、待处理、执行中、等待重试、累计尝试，最近命中/成功/失败时间。
- 生成记录：源作者/正文、记录状态、草稿标题、本轮尝试/上限、累计尝试、耗时、最近错误、查看草稿/重试。
- 运行日志：任务启停/修改、历史扫描、入队、每次执行开始与结果，关联源内容和生成记录。
- 已生成文章进入 `/articles`；详情能打开查看/编辑草稿，失败记录能单条或批量重试。

第一版不增加独立账号采集周期或定时汇总。没有新内容时任务显示“已启用 · 等待新内容”，而不是一直显示“运行中”。

## 3. 状态与统计定义

### 3.1 监听任务状态

| 状态 | 行为 |
| --- | --- |
| 已启用 | 新内容可以匹配；在依赖就绪时执行队列 |
| 已暂停 | 停止新命中和未开始记录的领取；领取事务已提交的执行允许完成 |
| 配置异常 | 所选账号全部不可用、所选 Skill 缺失/停用等导致无法按完整规则执行；停止新命中和未开始记录的领取 |
| 已归档 | 停止生成，隐藏于默认列表；保留记录、草稿、审计和防重数据 |

运行环境独立显示：AI 总开关关闭、数据源不可用、Worker 离线。这些是依赖异常，不应把每条空闲任务误标为执行失败。保存与执行时都做检查；依赖问题恢复后按既有队列继续执行。

账号部分不可用时提示“2/3 个账号可采集”，其余账号继续处理；全部不可用时显示配置异常。任务状态和依赖状态取后端计算结果。

恢复暂停任务继续处理暂停前已入队的记录。从恢复时刻重新监听新发布内容，暂停期间的内容不自动补生成；需要补处理时使用“补生成历史”，先预估数量再入队。

“执行开始”统一定义为领取事务提交，暂停/恢复与领取必须使用同一任务行锁串行化。归档时停止实时匹配、取消尚未领取的记录和未完成回溯；已经领取的执行允许完成，结果仍记入该任务历史。

### 3.2 单篇生成记录状态

`queued → running → succeeded`；可重试失败进入 `retry_wait → running`；尝试耗尽或不可重试错误进入 `failed`。需要取消时进入 `cancelled`，保留原记录。

- 成功数：当前 `succeeded` 的记录数量。
- 最终失败数：当前 `failed` 的记录数量。`retry_wait` 不算最终失败。
- 待处理数：`queued` 的数量；执行中、等待重试单独统计。
- 累计执行尝试：所有已开始的 Worker 执行次数，包含首次、失败、自动重试和手动重试；不是文章数量，也不承诺等于外部 API 调用次数。
- 本轮尝试：某轮重试预算里的 `attempts/max_attempts`，例如 2/3。
- 累计尝试：同一生成记录所有重试轮的总执行数，不因手动重试清零。
- 成功率：若显示，使用成功数 ÷（成功数 + 最终失败数）；排队、执行中、等待重试、取消不纳入。

例：一篇内容失败两次后成功，成功 1、最终失败 0、累计执行尝试 3；两次失败保留在日志里。最终失败记录被手动重试时，当前失败数减少、排队数增加，历史失败尝试仍可查看。

累计任务统计覆盖全部任务记录，包括已归档/隐藏的记录；记录清理不应意外重置累计审计统计。

## 4. 匹配、时间与防重

### 4.1 执行流程

```mermaid
flowchart LR
  A[已有账号采集器] --> B[源推文保存]
  B --> C[匹配启用的 AI 监听任务]
  C --> D[账号与模式过滤 / 时间边界 / 防重]
  D --> E[冻结任务配置与 Skills 指令]
  E --> F[持久化生成记录]
  F --> G[AI Worker 调用全局数据源]
  G --> H[文章草稿 / 最终失败]
  G --> I[尝试日志和任务统计]
```

监听任务复用现有采集器，针对已采集内容筛选。回复包含回复他人及自己的串文，转推包含引用转推，语义沿用现有 `tweet_types.py`。账号采集层没采集到的内容，AI 任务无法凭筛选自动补回。

“从启用时刻开始”严格按源内容 `posted_at >= effective_from` 匹配；以服务端 UTC 保存、界面按用户时区展示。晚采集到的、发布时间在边界之前的内容不会自动生成。首次选最近 N 天则在任务启动时固定 `cutoff = activated_at - N 天`，回溯边界不随后台扫描时间滑动。

实时匹配与历史回溯共享账号、模式、Skills 校验与防重规则；时间范围分别处理。实时匹配使用任务/订阅的有效时间；显式回溯使用固定的 `[from, to)`，不受实时 `effective_from` 下限影响，因此可以补处理暂停期间或任务新建之前的内容。

编辑任务的账号、模式、Skills 只影响后续新记录，不自动重跑历史。指定账号订阅保存各自的 `effective_from`，新加入账号从该订阅生效时刻开始；原订阅不因编辑而抬高下限。全部账号模式中，后来新增账号的边界取任务当前启用时间与账号加入采集时间的较晚者。恢复任务会推进任务级实时边界，但不会重写明确请求的回溯范围。

首次选择历史范围时，固定历史窗口为 `[activated_at - N 天, activated_at)`，实时窗口从 `activated_at` 开始；后续晚采集到的该历史窗口内容，可按保存的首次窗口匹配入队，窗口不会滑动。此规则仅适用于用户明确选择的首次回溯，恢复任务不自动新增暂停期间窗口。

### 4.2 防重和可追溯性

- 同一任务 + 同一源内容只自动生成一次；不同任务可以各生成一篇，因为其 Skills 可能不同。
- 推荐唯一键 `listen:{task_id}:tweet:{tweet_db_id}` 或数据库唯一约束 `(listen_task_id, source_tweet_id)`。
- 配置版本不放入防重键，编辑任务不会让旧内容重新生成。
- 失败重试沿用同一生成记录；复制任务得到新的任务 ID，可以按新配置独立生成。
- `/tweets` 手动生成记录标记来源为手动，不计入某个监听任务的统计。
- 归档任务、隐藏记录、删除草稿均须保留任务匹配账本/防重信息；不能靠删除生成记录重新执行。

现有删除监听账号会级联删除推文、生成记录和草稿。新增监听任务后，对存在生成历史的账号采用归档保留来源，而不是硬删除；界面要展示该行为。若后续支持物理清理，必须先保存独立的源内容快照、任务防重账本和尝试统计，并解除级联删除链。

Skill 指令和版本在入队时冻结：排队后修改 Skill 不改变已经创建的记录。任务选中的 Skills 是完整约束集合，不再叠加账号绑定和默认 Skills。所选 Skill 被停用或删除时，新入队必须阻止或将任务置为配置异常，禁止静默忽略其中某个 Skill。

入队时冻结语言、语气、重试预算等生成参数；执行时使用当前全局数据源，记录本次实际数据源名称、模型和版本。API Key 仅保存在数据源配置，不进入日志或任务快照。

## 5. 后端落点

### 5.1 新增与扩展实体

| 实体 | 关键字段 |
| --- | --- |
| `AIListenTask` | name、is_enabled、all_monitored_users、listen_mode、feature_code、config_version、effective_from、initial_sync_days、archived_at、生成参数覆盖值 |
| `AIListenTaskSubscription` | task_id、monitored_user_id、effective_from；复合唯一 |
| `AIListenTaskSkill` | task_id、skill_id、priority；复合唯一；保持选择顺序 |
| `AIListenTaskBackfill` | task_id、范围和配置快照、扫描游标、扫描/入队数、状态、错误、幂等 request_id |
| `AIGenerationJob` 扩展 | listen_task_id、trigger_type、task_snapshot、task_config_version、lifetime_attempts、归档标记 |
| `AIGenerationAttempt` | job_id、重试轮、序号、started_at、ended_at、结果、错误类型、错误摘要、耗时、实际模型/数据源版本 |
| `AIListenTaskEvent` | task_id、事件类型、关联 job/回溯批次、时间、摘要和必要数据 |

任务 Skills 可用关联表保存顺序；job 继续保存完整指令快照。生成记录关联任务建议保留外键并软归档任务；统计不依赖任务名称字符串。

现有 `retry_ai_job` 会清零 `attempts`，因此不能直接把它求和作为累计次数。追加式尝试记录和永不清零的 `lifetime_attempts` 在 Worker 领取事务中更新，事件写入与状态提交保持一致。

### 5.3 复用现有执行基础

- 在 `services/poller.py` 保存新推文的事务内批量匹配任务、创建生成记录。沿用现有事务 outbox，避免源内容保存成功但漏入队。
- `services/ai_jobs.py` 扩展自动入队：批量读取配置/关联，任务显式 Skills，实际插入行用 `RETURNING` 计数；并发由数据库唯一约束去重。
- 回溯后台分批扫描，保存游标并可恢复；创建 API 不同步扫描大量历史。暂停任务时停止扫描和入队并保留游标；恢复继续此前明确请求的回溯，这与不自动补暂停期间内容分别处理。归档取消未完成回溯。
- `ai_worker.py` 保留锁、claim token、租约和失败退避；扫描候选和最终领取事务都校验任务/AI 总开关。领取与任务状态修改通过任务行锁串行化，防止暂停后继续领取。
- 过期租约清理与重新领取分离：暂停/归档任务仍允许清理过期 `running`，结束旧尝试并标记 interrupted/lease_expired，转回待处理（暂停）或取消（归档）；清理不调用 AI，只有有效启用任务能够重新领取。
- 单任务配置异常不能抛出并破坏整个账号采集事务或其他任务；记录阻塞原因，跳过该任务。
- 列表/详情的聚合统计在后端查询，支持筛选时间段；前端活跃页面轻量刷新，隐藏后停止。
- 多任务生成会竞争写入同一作者画像，画像更新需要按源内容时间/版本防止旧任务覆盖新画像，或把画像维护独立于写作任务。

## 6. 现有自动生成的迁移

当前“采集后自动生成”对所有新采集推文建立 `auto:{tweet_id}`，按账号绑定或默认 Skills 生成。不能与监听任务入口同时入队，否则同一原文会多出一篇用户没配置的文章。

推荐新增明确触发模式 `legacy_all / listening_tasks`：新安装默认监听任务模式；已有安装保留兼容模式直到用户显式迁移。在第一次启用监听任务前展示实际影响摘要，用户切换后仅按启用任务自动生成，旧待处理记录继续按原快照完成并标记“旧自动生成”。

触发模式切换、首任务启用与生效时间在同一事务提交；采集事务的触发路由与模式修改持有同一设置行锁，明确切换边界。迁移前既有源内容默认由旧记录覆盖，新的监听任务从切换时刻开始；如用户主动回溯，预览列出已被旧流程生成的数量，并默认排除，可显式选择按新 Skills 再生成。

旧账号 Skill 绑定保留用于兼容模式和手动生成默认值；新监听任务必须完整选定自身 Skills。AI 总开关继续控制允许创建/执行，原自动生成开关在任务模式下作为全局自动监听开关，不再代表对全部账号无条件生成。

不根据旧配置静默创建使用空 Skills 的任务，不丢弃旧生成记录，不把旧统计混入新任务。

## 7. 第一版交付范围与验收

第一版：监听任务新增/编辑/复制/暂停恢复/归档、账号范围和模式、多选 Skills、首次历史范围和补生成、复用全局数据源、服务端统计、生成记录关联、失败重试、尝试日志。

后续按需求增加：关键词过滤、日配额、跨账号汇总、定时汇总、任务独立数据源和自动发布。

关键验收：

1. 选择 A/B 两账号、仅原创和两项 Skills，其他账号/回复/转推不生成；所选两项 Skill 指令都进入请求。
2. 同一推文重复采集、实时与回溯重叠、并发扫描均只在同任务内生成一次；另一任务可独立生成。
3. 编辑 Skills 不改变既有快照、不自动重跑；停用 Skill 不悄悄减少约束。
4. 暂停后无新领取提交，已领取的执行可完成；恢复继续原队列和已请求回溯，不自动补暂停期间内容；显式历史回溯可覆盖早于恢复时刻的内容。
5. 两次失败后成功显示成功 1、最终失败 0、累计尝试 3；手动重试保留所有历史。
6. Worker 重启、租约过期、历史扫描中断能够恢复；同记录只持久化一篇草稿。
7. 归档/隐藏保留草稿、记录和防重信息；列表统计不受分页影响。
8. 全局兼容模式与任务模式互斥入队；手动生成不污染任务统计。
9. 本方案的交互预览使用示例数据，不触发账号采集、AI 请求或自动发布。
