## 5. 阶段三：首次执行与发现的问题

### tc-2 首次安装

已将脚本上传为 `/root/kejilion.sh`，应用配置为 `/root/apps/auto-x.conf`，源码为 `/root/auto-x-source`。执行入口如下（Nacos 密码通过隐藏输入提示录入，不放进命令参数）：

```bash
cd /root
KJ_APPS_SKIP_REFRESH=1 KJ_AUTO_X_SOURCE_DIR=/root/auto-x-source \
KJ_APP_NONINTERACTIVE=1 KJ_APP_ACTION=install KJ_APP_PORT=8080 \
AUTO_X_SERVICES=backend,worker,ai-worker,qq-worker,auth-center,monitor-agent,frontend \
bash kejilion.sh apps auto-x
```

安装器自行安装 rsync，Nacos 连接及认证通过，生成受保护 `.env`、认证文件，启动了七个所选组件及 PostgreSQL、Redis。首次安装正常退出。其后发现默认注册地址为 tc-2 内网地址，故增加显式注册地址与节点身份参数，并再次通过安装入口更新。

### tc-1 首次安装与中断

按相同入口选择 `xhs-worker,monitor-center,monitor-agent`，设置注册地址 `118.25.197.211`，认证中心地址 `http://43.172.88.37:9100`。Nacos 校验通过，XHS 与 backend 镜像下载完成。首次在基础镜像下载期间 SSH 连接关闭；重试后 PostgreSQL 镜像仍长时间无进展，主动停止重试并排查依赖。此时 tc-1 没有启动 Auto-X 容器，原有 Nacos 保持运行。

### 定位出的实际问题

1. **数据依赖仍是单机模式**：基础 Compose 的 xhs-worker 依赖 migrate，migrate 依赖本机 PostgreSQL/Redis。Nacos 当前地址为 `postgres`/`redis`，tc-1 会启动另一套数据库，不能实现共享数据。修复方向：Nacos 改用 tc-2 可达地址，tc-2 显式管理数据服务，tc-1 使用 external override。
2. **监控节点身份不匹配**：更新 `MONITOR_NODE_ID=tc-2` 后，旧 `services.json` 仍只有 `local`，monitor-agent 因此重启。其余 tc-2 业务容器健康。修复方向：新增专用双节点拓扑 `infra/microservices/services.tc-dual.json`，部署到双方控制平面目录，保留通用单机示例。
3. **上传源码不等于运行源码**：原安装器只同步文件，再拉 registry 镜像并 `up --no-build`，不会把 dev 源码装入容器。修复方向：增加显式源码构建模式，由同一安装入口构建后启动，防止再次 pull 覆盖构建产物。
4. **监控跨节点授权**：默认监控客户端只具有 `agent:local` 授权，双节点需补充 `agent:tc-1`、`agent:tc-2` 的 `resources:read` 授权；同时两节点共享 monitor 客户端密钥。
5. **macOS 打包元数据噪声**：tar 初次上传有扩展属性警告，后续使用禁用 macOS 元数据的归档并缩小为实际源码文件，上传后核对关键文件摘要。

### 安装器问题修复

首次重试时，`kejilion.sh` 定义的 `install` 函数遮蔽了系统 `install` 命令，复制拓扑文件时把 `-o/-g/-m` 当成 apt 参数，产生非致命的 `Option -o requires an argument` 等输出。已在本地 `auto-x.conf` 改为 `command install`，并将修复后的文件同步到两台服务器；拓扑复制随后由校验后的 fallback 完成。

为应对 Docker registry 基础镜像下载缓慢，安装器新增显式 `KJ_AUTO_X_SKIP_PULL=1`：仅当本节点已存在所有选定服务及本地数据依赖镜像时跳过 registry 拉取，默认行为仍保持拉取和失败回退。tc-1 使用该模式启动成功。
