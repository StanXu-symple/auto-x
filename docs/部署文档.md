## 5. 阶段三：首次执行与发现的问题

### tc-2 首次安装

已将脚本上传为 `/root/kejilion.sh`，应用配置为 `/root/apps/auto-x.conf`，源码为 `/root/auto-x-source`。执行入口如下（Nacos 密码通过隐藏输入提示录入，不放进命令参数）：

```bash

```

安装器自行安装 rsync，Nacos 连接及认证通过，生成受保护 `.env`、认证文件，启动了七个所选组件及 PostgreSQL、Redis。首次安装正常退出。其后发现默认注册地址为 tc-2 内网地址，故增加显式注册地址与节点身份参数，并再次通过安装入口更新。

### tc-1 首次安装与中断

按相同入口选择 `xhs-worker,monitor-center,monitor-agent`，设置注册地址 `118.25.197.211`，认证中心地址 `http://43.172.88.37:9100`。Nacos 校验通过，XHS 与 backend 镜像下载完成。首次在基础镜像下载期间 SSH 连接关闭；重试后 PostgreSQL 镜像仍长时间无进展，主动停止重试并排查依赖。此时 tc-1 没有启动 Auto-X 容器，原有 Nacos 保持运行。

### 定位出的实际问题

1. **数据依赖仍是单机模式**：基础 Compose 的 xhs-worker 依赖 migrate，migrate 依赖本机 PostgreSQL/Redis。Nacos 当前地址为 `postgres`/`redis`，tc-1 会启动另一套数据库，不能实现共享数据。修复方向：Nacos 改用 tc-2 可达地址，tc-2 显式管理数据服务，tc-1 使用 external override。
2. **监控节点身份不匹配**：更新 `MONITOR_NODE_ID=tc-2` 后，旧 `services.json` 仍只有 `local`，monitor-agent 因此重启。其余 tc-2 业务容器健康。修复方向：新增专用双节点拓扑 `infra/microservices/services.tc-dual.json`，部署到双方控制平面目录，保留通用单机示例。
3. **上传源码不等于运行源码**：原安装器只同步文件，再拉 registry 镜像并 `up --no-build`，不会把 dev 源码装入容器。修复方向：增加显式源码构建模式，由同一安装入口构建后启动，防止再次 pull 覆盖构建产物。
4. **监控跨节点授权**：默认监控客户端只具有 `agent:local` 授权，双节点需补充 `agent:tc-1`、`agent:tc-2` 的 `resources:read` 授权；同时两节点共享 monitor 客户端密钥。
5. **macOS 打包元数据噪声**：tar 初次上传有扩展属性警告，后续使用禁用 macOS 元数据的归档并缩小为实际源码文件，上传后核对关键文件摘要。

## 11. 统一切换到 tc-2 PostgreSQL/Redis（2026-09-23）

### 切换方案

Nacos 中继续保留逻辑主机名 `POSTGRES_HOST=postgres`、`REDIS_HOST=redis` 以及 tc-2 生成的统一账号、密码、数据库名。tc-2 通过 Docker 网络中的 `postgres`、`redis` 直接访问本机数据容器；tc-1 设置 `AUTO_X_MANAGE_DATA=false`，并通过安装器生成 `docker-compose.data-routing.yml`，在 tc-1 业务容器内将两个逻辑名解析到 `43.172.88.37`。这样避免 tc-2 容器访问自身公网地址的回环限制，也避免把共享地址写成会影响 tc-2 的公网地址。

### 执行与修复

第一次执行 `KJ_APP_ACTION=update` 被 kejilion 的通用生命周期检查拒绝，因为 tc-1 是 worker/监控节点，没有 `x-sentinel-frontend-1`。已修改 Auto-X 应用配置：已有节点根据 `.auto-x-services` 选择实际存在的长期运行容器作为更新检查对象，仍然使用同一 `bash kejilion.sh app auto-x` 入口。随后重跑 update 成功，输出 `Auto-X 已从 GitHub 项目更新完成` 和 `应用更新完成`。

### 连接验证

- tc-1 的容器内 `getent hosts postgres redis` 均返回 `43.172.88.37`。
- tc-1 xhs-worker 通过 PostgreSQL 查询得到服务器地址 `172.20.0.4/32`，数据库为 `xsentinel`、用户为 `xsentinel`；tc-2 PostgreSQL 容器地址为同一个 `172.20.0.4`。
- tc-1 Redis 查询得到 run_id `a838e0d0e2f6fce8f6fa568a8fb5e38eb53e700e`，tc-2 Redis 查询得到相同 run_id，证明两节点使用同一个 Redis 实例。
- 切换后 tc-1 的 xhs-worker、monitor-center、monitor-agent 仍 healthy；8006、9101、9102 健康接口均成功。
- tc-1 原有 PostgreSQL/Redis 容器已停止，旧数据目录和容器卷保留，没有删除，便于回退。tc-1 主机本地 5432/6379 已无监听。

### 当前数据拓扑

tc-2 是唯一运行的 PostgreSQL/Redis 数据节点；tc-1 只运行 `xhs-worker`、`monitor-center`、`monitor-agent`，通过 tc-2 的 5432/6379 访问共享数据。tc-2 入站规则仍只需允许来源 `118.25.197.211/32` 的 TCP 5432、6379。
